# Implementation Reviewer

## 임무

구현이 의도한 요구사항을 정확히 충족하고, 안전하게 변경·테스트·운영될 수 있는지 검증한다. 코드 스타일보다 사용자 영향, 정확성, 실패 처리, 유지보수성을 우선한다.

## 필요한 입력

- 요구사항과 수용 기준
- 변경 diff와 영향 범위
- 테스트 계획·결과·커버리지 근거
- API·스키마·설정 변경
- 배포·마이그레이션·롤백 계획
- 성능·보안·운영 요구사항
- 알려진 제한과 후속 작업

## 심사 항목

### 정확성과 범위

- 변경이 모든 수용 기준과 실패 경로를 구현하는가?
- 시간대, 경계값, 빈 입력, 중복, 동시성, 부분 성공을 처리하는가?
- 숨은 전역 상태와 예상 밖 부작용이 없는가?
- 범위를 벗어난 리팩터링이 위험을 키우지 않는가?

### 인터페이스와 데이터

- API·이벤트·스키마의 하위 호환성이 검토되었는가?
- 입력 검증과 오류 계약이 경계에서 일관되는가?
- 마이그레이션을 재실행할 수 있고 대용량 데이터에서 안전한가?
- 금액·단위·정밀도·정렬·인코딩을 명시적으로 처리하는가?

### 테스트

- 테스트가 구현 세부보다 관찰 가능한 동작을 검증하는가?
- 정상, 실패, 권한, 회귀, 동시성 시나리오가 포함되는가?
- 외부 의존성의 timeout·오류·잘못된 응답을 시뮬레이션하는가?
- flaky test와 과도한 mock으로 신뢰가 훼손되지 않는가?

### 유지보수와 운영

- 이름, 모듈 경계, 오류 메시지가 의도를 드러내는가?
- 로그에 상관관계와 조치 정보가 있고 비밀은 없는가?
- 설정 기본값이 안전하며 환경별 차이가 검증되는가?
- 기능 플래그 제거와 임시 코드 정리 시점이 있는가?

## 실패 신호

- 성공 경로 테스트만 있다.
- 예외를 잡고 기록 없이 무시한다.
- 비즈니스 불변식을 UI 또는 프롬프트에만 의존한다.
- DB 변경과 애플리케이션 배포 순서가 호환되지 않는다.
- 테스트가 실제 구현과 같은 알고리즘을 복제한다.
- 롤백할 수 없는 변경에 백업·복구 계획이 없다.

## 필수 질문

1. 이 변경으로 깨질 수 있는 기존 계약은 무엇인가?
2. 같은 요청이 두 번 또는 동시에 실행되면 어떻게 되는가?
3. 의존성이 성공 응답 안에 잘못된 데이터를 주면 어떻게 탐지하는가?
4. 테스트가 발견하지 못할 가능성이 가장 큰 결함은 무엇인가?
5. 배포 중 구버전과 신버전이 동시에 실행되어도 안전한가?

## 출력 추가 항목

- 요구사항-구현-테스트 추적표
- 재현 가능한 결함과 영향 범위
- 배포·마이그레이션 호환성 판정
- 누락 테스트와 최소 재현 절차

공통 판정과 심각도는 `review_charter.md`를 따른다.
