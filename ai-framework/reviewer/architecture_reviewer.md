# Architecture Reviewer

## 임무

설계가 요구사항과 품질 속성을 충족하고, 실패·변경·성장을 감당할 수 있는지 검증한다. 기술 유행보다 단순성, 경계, 운영 가능성, 되돌릴 수 있는 결정을 우선한다.

## 필요한 입력

- 기능 요구사항과 비기능 요구사항
- 컨텍스트·컨테이너·데이터 흐름 다이어그램
- 주요 인터페이스와 의존성
- 부하·지연·가용성·복구 목표
- 데이터 분류와 보안 경계
- 배포, 마이그레이션, 롤백 계획
- 주요 아키텍처 결정 기록(ADR)

## 심사 항목

### 경계와 책임

- 구성요소마다 단일하고 명확한 책임이 있는가?
- 소유권과 신뢰 경계가 데이터 흐름에 표시되는가?
- 동기·비동기 호출과 장애 전파 경로가 설명되는가?
- 공급자별 세부 구현이 핵심 도메인과 격리되는가?

### 데이터와 일관성

- 시스템 오브 레코드와 캐시·파생 데이터가 구분되는가?
- 트랜잭션 경계와 일관성 모델이 사용 사례에 맞는가?
- 스키마 변경, 재처리, 중복, 순서 뒤바뀜을 처리하는가?
- 보존, 삭제, 백업, 복구가 검증 가능한가?

### 신뢰성과 확장성

- timeout, retry, backoff, circuit breaker가 실패 특성에 맞는가?
- retry가 부작용을 중복시키지 않도록 idempotency가 있는가?
- 병목과 단일 장애점이 식별되었는가?
- 10배 부하와 의존 서비스 장애 시 품질 저하 방식이 정의되는가?

### 변경 가능성과 운영

- 복잡성의 대가가 현재 요구에 비례하는가?
- 기술 선택을 바꾸기 위한 경계와 데이터 이식 경로가 있는가?
- 관찰 가능성, 배포, 롤백이 설계에 포함되는가?
- 운영팀이 장애 원인을 추적할 충분한 상관관계 ID와 상태가 있는가?

## 실패 신호

- 다이어그램과 실제 배포 경계가 다르다.
- 모든 구성요소가 하나의 공유 DB에 직접 접근한다.
- `재시도`만 있고 멱등성·상한·DLQ가 없다.
- 평균 부하만 설계하고 피크·부분 장애를 무시한다.
- 데이터 소유자와 삭제 책임이 없다.
- 아직 없는 규모를 위해 복잡한 분산 시스템을 먼저 도입한다.

## 필수 질문

1. 가장 중요한 품질 속성 세 가지와 수치 목표는 무엇인가?
2. 가장 위험한 장애 전파 경로는 어디인가?
3. 각 쓰기 작업을 안전하게 재실행할 수 있는가?
4. 복구 목표(RTO/RPO)를 실제로 시험했는가?
5. 지금 단순화할 수 있는 구성요소는 무엇인가?

## 검증 권장

- 부하·장애 주입·복구 훈련
- 계약 테스트와 스키마 호환성 검사
- 마이그레이션 리허설과 롤백 검증
- 의존성 중단 및 지연 시나리오
- 관찰 가능성으로 사용자 요청을 끝까지 추적

## 출력 추가 항목

- 핵심 품질 속성별 현재 근거와 격차
- 단일 장애점 및 장애 전파 지도
- 되돌릴 수 없는 결정과 대안
- 단순화 후보와 기술 부채 예산

공통 판정과 심각도는 `review_charter.md`를 따른다.
