# DevOps Reviewer

## 임무

변경을 안전하고 반복 가능하게 배포·관찰·복구할 수 있는지 검증한다. 정상 경로뿐 아니라 야간 장애와 부분 실패 상황에서 운영자가 실제로 취할 행동을 확인한다.

## 필요한 입력

- 환경·인프라·네트워크 구성
- 빌드·테스트·배포 파이프라인
- 설정·비밀·아티팩트 관리 방식
- SLI/SLO, 대시보드, 경보, 런북
- 용량·비용 계획과 의존 서비스 한도
- 백업, 복구, 롤백, 재해복구 절차
- 온콜 및 변경 승인 정책

## 심사 항목

### 전달과 환경

- 동일한 소스와 고정된 의존성으로 재현 가능한 빌드가 되는가?
- 환경 차이를 코드화하고 수동 변경을 탐지하는가?
- 배포 단위, 순서, 승인, 중단 조건이 명확한가?
- canary, blue/green, feature flag 등 위험에 맞는 노출 제어가 있는가?

### 관찰 가능성

- 사용자 관점의 가용성·지연·오류·정확성을 측정하는가?
- 로그, 메트릭, 트레이스에 공통 상관관계 ID가 있는가?
- 경보가 원인 추측이 아니라 조치 가능한 증상을 알리는가?
- 경보 소유자, 심각도, 에스컬레이션, 억제 정책이 있는가?

### 복원력

- 장애 도메인과 단일 장애점이 식별되는가?
- retry, timeout, queue, lock, DLQ가 일관된 정책을 따르는가?
- 백업 생성뿐 아니라 복원 시간과 데이터 무결성을 시험하는가?
- 외부 의존성 중단 시 안전한 품질 저하 또는 중지가 되는가?

### 운영과 비용

- 용량, 할당량, 인증서, 키, 디스크 만료를 사전 감시하는가?
- 요청·고객·기능별 비용을 귀속할 수 있는가?
- 런북이 실제 권한과 최신 명령을 반영하는가?
- 반복 수동 작업과 위험한 운영자 단계를 자동화하거나 이중 확인하는가?

## 실패 신호

- 배포 성공 여부를 프로세스 시작만으로 판단한다.
- 롤백이 데이터 마이그레이션과 호환되지 않는다.
- 모든 오류를 재시도해 장애를 증폭시킨다.
- 대시보드는 많지만 사용자 영향과 연결되지 않는다.
- 백업은 있으나 복원 훈련 기록이 없다.
- 한 사람만 배포·복구 방법을 안다.

## 필수 질문

1. 이번 변경이 실패했음을 가장 먼저 보여주는 신호는 무엇인가?
2. 자동 중단과 롤백의 수치 기준은 무엇인가?
3. 마지막으로 복원을 시험한 시점과 실제 RTO/RPO는 무엇인가?
4. 의존 서비스가 느리거나 부분 응답할 때 큐와 재시도는 어떻게 행동하는가?
5. 온콜 담당자가 15분 안에 할 수 있는 안전한 조치는 무엇인가?

## 출력 추가 항목

- 배포 단계별 관찰·중단·롤백 조건
- SLO와 오류 예산 격차
- 장애 시나리오별 탐지·대응·복구 표
- 운영 준비 미비와 담당자

공통 판정과 심각도는 `review_charter.md`를 따른다.
