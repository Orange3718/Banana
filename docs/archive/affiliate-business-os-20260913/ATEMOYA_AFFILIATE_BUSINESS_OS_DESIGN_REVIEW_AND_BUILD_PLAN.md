## 1. 판정

**REVIEW — 사업 방향은 타당한 가설이며, 상세 설계로 발전시킬 수 있다. 현재 문서를 그대로 운영 구현에 사용하는 것은 NO-GO다.**

후속 상세 설계와 격리된 검증 작업은 CONDITIONAL GO다. 아래 G0·G1 조건을 해결하며 진행할 수 있다. 실제 유입을 받는 운영 출시는 G2까지 통과해야 한다.

문서는 순현금흐름, 구매 의도, 제휴사별 정책, 운영 책임, 검증 후 확장을 잘 제시한다. 그러나 매출 귀속, 수수료 정정과 입금, 클릭 수집의 공개 경계, 승인 상태, 장애 복구를 구현할 계약이 부족하다. 기능 목록과 목표 아키텍처로는 유용하지만, 아직 구축용 상세 명세는 아니다.

설계 결함 존재에 대한 신뢰도는 High다. 실제 시장 수익성·제휴 승인·전환율은 Unknown이다. 이 리뷰의 점검 결과로 사업 성공 가능성을 수치화하지 않는다.

## 4. 우선 수정할 발견 사항

P1은 해당 기능의 운영 출시를 막는 설계 위험이다. P2는 상세 설계 또는 확장 전에 해결할 항목이다. 구축 전 문서이므로 실제 사고·취약점이 재현됐다는 의미가 아니다. 담당자는 역할로 배정했으며, 실명은 G0에서 지정한다. 기한은 달력 날짜 대신 반드시 해결해야 하는 게이트로 표시한다.

### R01 — P1 / Likely: 콘텐츠별 수익 귀속을 증명할 연결 정보 부족

- 근거: §10.2, §11.7–11.10, §14.9, §36. 클릭에는 콘텐츠 ID가 있지만 전환에는 콘텐츠·배치·추적 ID가 없다. `affiliate_item_id`만으로 글을 역추적할 수 없는 경우가 생긴다.
- 영향: 같은 상품을 글 A와 B가 추천하면 어느 글이 벌었는지 분리하지 못한다. 클릭한 상품과 구매한 상품이 달라도 잘못 매칭될 수 있다.
- 확인 질문: 실제 보고서가 반환하는 식별자는 주문·상품·tracking ID·sub-ID 중 무엇이며 어느 단위로 집계되는가?
- 개선: 공급자 capability, 불변 `link_id`, 추적 ID 매핑, 귀속 수준을 도입한다. 구분 불가능한 매출은 미귀속으로 보존한다. 모든 공급자가 클릭별 전환 연결을 제공한다고 가정하지 않는다.
- 완료 조건: 익명화한 실제 형식 보고서를 써서 A/B 글 동일 상품과 다른 상품 구매를 검증하고, 연결 불가능한 행을 억지 배분하지 않는다.
- 소유자 / 기한: 데이터 담당 + 제휴 운영 / G1.

### R02 — P1 / Likely: 순현금흐름 목표를 현재 수익·비용 모델로 계산할 수 없음

- 근거: §2, §11.9–11.11, §15, §17. 수수료·수익 연결키, 지급 배치, 입금일, 환불 조정, 비용 귀속과 지급일이 없다.
- 영향: 전환과 수익을 각각 합산해 이중 집계하거나, 승인 전 수수료를 현금처럼 보고하거나, 취소된 수익을 계속 이익으로 표시할 수 있다.
- 확인 질문: 공급자의 주문·확정·지급·실제 입금을 각각 어떤 자료로 증명하는가?
- 개선: 상태별 수수료와 지급·입금 기록을 분리한다. 비용은 현금지출·직접비·공통비·Owner 시간을 분리하고 다중 통화를 변환 근거와 함께 기록한다.
- 완료 조건: §8의 가상 정산 사례와 중복 수입 검증을 통과하고, 예상 수익·공헌이익·순현금흐름이 서로 다른 값으로 설명된다.
- 소유자 / 기한: 데이터 담당 + 재무 검토 / G1.

### R03 — P1 / Possible: GitHub Pages를 상업 운영의 기본 호스트로 유지하는 전제

- 근거: §29, §31과 기존 운영 기준의 GitHub Pages 경로. GitHub 공식 문서는 온라인 사업 또는 상거래 촉진이 주목적인 사이트의 무료 호스팅 용도를 제한한다. [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), 확인 2026-09-13.
- 영향: 원문이 명시한 제휴 구매·예약 유도 중심 사업은 이 제한과 충돌할 가능성이 있어 호스팅 중단·이전 비용을 초래할 수 있다. 이 리뷰는 실제 서비스에 대한 약관 위반 확정 판정은 아니다.
- 확인 질문: 선택할 운영 호스팅이 이 사업 형태를 허용하는가?
- 개선: GitHub는 소스·검토·빌드 기준점으로 유지하고, 운영 호스팅은 상업 이용 조건과 비용을 확인해 별도 결정한다. 기존 URL의 유지·이전·canonical 정책도 ADR에 포함한다.
- 완료 조건: 호스팅 허용 범위, 도메인, 배포·롤백 방식, 비용이 기록된 ADR 승인.
- 소유자 / 기한: 아키텍처 담당 + Owner / G0.

### R04 — P1 / Possible: 공개 클릭 수집과 비공개 운영 시스템의 경계가 없음

- 근거: §10.2, §14.8, §31. 웹사이트 이벤트가 DB에 도착하는 경로의 호스트·인증·제한·장애 처리 미정.
- 영향: 수집 API의 악용으로 DB를 오염시키거나 고갈시킬 수 있다. 클릭 이동을 수집 응답에 묶으면 수집 장애가 구매 이동도 막는다. 내부 편집기·DB 공개로 이어지는 구현도 배제되지 않았다.
- 확인 질문: 외부 방문자가 접근할 유일한 endpoint와 허용 이벤트는 무엇인가?
- 개선: 제한된 이벤트 수집 경로만 공개하고 n8n 편집기·DB는 비공개로 유지한다. 직접 제휴 링크 이동과 비동기 측정을 분리한다. 공개 웹의 이벤트는 완전한 신원 증명이 불가능하므로 검증·속도 제한·봇 분류를 함께 적용한다.
- 완료 조건: 잘못된 link ID·재전송·과대 요청 거부, 수집 장애 시 구매 이동 성공, 내부 주소 접근 차단 테스트.
- 소유자 / 기한: Backend + 보안 / G2.

### R05 — P1 / Possible: 승인과 게시 상태가 충분히 정의되지 않음

- 근거: §1은 대부분 자동 처리를 지향하고 §13.7은 QA 통과 후 게시, §14.7은 `Approved content`로 시작한다. §11.15 승인 항목에는 승인 대상 버전·권한·만료가 없다. 기존 운영 기준은 개별 게시 승인을 사용한다.
- 영향: QA 통과를 사람 승인으로 혼동하거나, 승인 뒤 내용·링크가 바뀐 버전을 게시할 수 있다.
- 확인 질문: 초기 파일럿에서 누가 어떤 버전의 게시를 승인하며 승인 후 변경을 어떻게 처리하는가?
- 개선: `content_revision + policy_version + action + scope`에 승인 연결. 변경 시 재검토하고, Telegram 송신자 권한과 재전송을 검증한다. 기존 승인을 재사용할 때 의미와 상태를 먼저 매핑한다.
- 완료 조건: 승인 거절·만료·다른 버전·잘못된 사용자·동일 승인 재사용을 모두 처리한다.
- 소유자 / 기한: Backend + 운영 + Owner / G2.

### R06 — P1 / Likely: 전환 재수입·배포 부분 성공에 대한 중복 방지 부재

- 근거: §11, §14, §34는 retry를 언급하지만 고유키·트랜잭션·부분 성공 복구가 없다. §12의 `KEEP → PUBLISH`는 유지 결정을 재게시로 구현하게 만들 여지가 있다.
- 영향: 겹치는 보고서 재수입으로 매출이 중복되거나, 배포 성공 후 DB 기록 실패 시 중복 게시·알림이 발생한다.
- 확인 질문: 각 쓰기 작업의 재실행 고유키와 이미 완료된 외부 효과를 찾는 방법은 무엇인가?
- 개선: 작업별 idempotency key, attempt, lease, 재처리·격리 정책을 정의한다. KEEP는 현 상태 유지로 변경한다. 배포 식별자로 외부 결과를 조회한 후 DB를 복구한다.
- 완료 조건: 동일 보고서 2회·중첩 기간 보고서·수정 보고서·배포 후 프로세스 종료 사례에서 잔액과 공개 버전이 정확하다.
- 소유자 / 기한: Backend + DevOps / 정산은 G1, 게시는 G2.

### R07 — P1 / Likely: 첫 제휴사의 실제 사용 가능성과 측정 가능성 검증이 늦음

- 근거: §9는 추상 adapter, §32는 카테고리 출시 다음 단계에 귀속 검증, §41은 콘텐츠 생산 뒤 첫 보고서 수입을 둔다.
- 영향: 해외 방문자가 결제·배송·예약을 못 하거나, 프로그램 가입·도메인 승인이 안 되거나, 보고서가 원하는 단위를 제공하지 않아 실험 전체를 다시 설계해야 할 수 있다.
- 확인 질문: 첫 고객이 실제 구매할 수 있고 운영자가 승인·정산받을 수 있는 경로는 무엇인가?
- 개선: 계정 승인·대상 시장·등록 도메인·링크 생성·보고서 샘플 검증을 첫 파일럿보다 앞에 둔다. CSV 수동 수입도 허용해 API 자동화와 사업 검증을 분리한다.
- 완료 조건: 공급자 한 곳의 capability 검증표와 실제 형식 보고서 테스트가 G1을 통과한다. 계약·계정이 미확정이면 공개 파일럿을 시작하지 않는다.
- 소유자 / 기한: 제휴 운영 + 데이터 담당 / G1.

### R08 — P2 / Likely: 표본·보고 지연 없이 EXPAND/KILL 판단 가능

- 근거: §19의 `some of`, 첫 전환 1건, §20의 `enough`, §22의 `encouraging`, §23의 `positive`에는 수치·표본·성숙 기간이 없다. §22의 30일 KILL 후보와 §21의 90일 포트폴리오 결정도 관계가 불명확하다.
- 영향: 초기 우연·지연 전환·추적 누락을 성과로 해석해 잘못 확장하거나 중단한다.
- 개선: 데이터 상태와 경영 결정을 분리하고 `WAIT_FOR_DATA`를 둔다. 7/30/90일은 검토 날짜이며 자동 확정 기준으로 사용하지 않는다. 프로그램 보고·취소 기간이 지난 자료로 판단한다.
- 완료 조건: 같은 입력으로 같은 결정 사유가 나오며, 데이터 미수집·지연·소표본에 자동 EXPAND/KILL이 발생하지 않는다.
- 소유자 / 기한: 분석 + 사업 담당 / G3.

### R09 — P2 / Likely: 점수와 카테고리 확대가 근거보다 앞섬

- 근거: §7의 가중치는 합계 100이나 각 점수의 정규화·출처·역방향 항목 처리·누락값 처리 미정. §18·32는 5개 후보에 각 10–20개 자산을 제시해 50–100개까지 확대될 수 있다. §41은 3–5개로 다른 기준을 제시한다.
- 영향: AI가 인위적으로 정밀한 점수를 만들어내고, 매출 원인 확인 전에 유지비·콘텐츠 부담이 커진다.
- 개선: 자격 조건 → 증거 충족 → 점수 순으로 평가한다. 첫 실험은 고객군 1개·시장 1개·언어 1개·제휴사 1개·콘텐츠 3–5개를 기본 제안으로 둔다. 카테고리 선정 자체는 수요·제휴 검증 후 결정한다.
- 완료 조건: 점수 입력 근거와 버전을 재현할 수 있으며 누락 데이터는 낮은 점수로 위장되지 않는다.
- 소유자 / 기한: 사업 + 분석 / G0 및 G3.

### R10 — P2 / Possible: 사실 확인·독창성·콘텐츠 수명주기 계약 부족

- 근거: §13.6·14.5에는 체크 명칭만 있고 claim별 근거, 유효기간, 검토자, 샘플 평가가 없다. §26의 URL 유효성만으로 가격·품절·예약 가능성을 확정할 수 없다.
- 영향: 사실 오류·오래된 가격·근거 없는 추천이 QA를 통과하고, 비교표 형태만 갖춘 저가치 콘텐츠가 쌓일 수 있다.
- 개선: 근거가 있는 선택 기준·장단점·부적합 고객을 페이지마다 요구한다. 주장-출처-확인일과 이미지 사용권을 연결하고, 사실 검토·형식 검사를 분리한다. 공급자 정책에 맞는 자료 갱신·보존 기준을 둔다.
- 완료 조건: 알려진 오류·가짜 후기·오래된 근거·주입 공격 평가 세트가 차단되며, 새 초안은 독립 검토를 거친다. G2 전 해결.
- 소유자: 콘텐츠 + AI QA. Google은 대량의 저부가가치 콘텐츠와 복제형 제휴 콘텐츠를 스팸 정책에서 다룬다. AI 사용 자체나 일정 게시 수만으로 위반이 정해지는 것은 아니다. [공식 정책](https://developers.google.com/search/docs/essentials/spam-policies).

### R11 — P2 / Likely: 기존 DB·게시 자동화와의 호환 계획 부재

- 근거: §11은 새 필드 목록, §29–30은 기반·미완료 목록이다. 실제 기존 DB에 같은 이름의 테이블이 있고 저장소 migration 001의 필드·상태가 원안과 다르다. 기존 비용 테이블명은 `cost`다.
- 영향: `CREATE TABLE IF NOT EXISTS`로 새 필드가 생긴다고 오해하거나, 두 수익 원장·두 게시 실행기가 병존할 수 있다.
- 개선: 테이블·뷰·워크플로별 재사용/확장/신설 매핑을 작성한다. additive migration과 읽기 호환 뷰를 검토하고, 원장 소유자와 게시 실행기를 하나로 정한다.
- 완료 조건: 격리 DB에서 구버전 소비자와 신버전 흐름의 회귀·복구 검증. 운영 migration 전 필수.
- 소유자 / 기한: DBA + 운영 / G0–G1.

### R12 — P2 / Possible: Owner 최소 개입을 운영할 한도·책임이 없음

- 근거: §1·2·37–39는 Owner 시간·보고·장애 대응 목표를 제시하지만 작업별 예산, 에스컬레이션, 시간 기록, 복구 목표가 없다. 신규 문서는 유료 도구를 배제하지 않지만 기존 운영 기준은 로컬 우선·무료 보조 경로다.
- 영향: 과도한 알림, 수작업 정산, 모델 비용으로 순현금과 시간 목표를 달성하지 못할 수 있다.
- 개선: Owner 시간과 운영 작업을 측정하고, 위험·비용 범위가 정해진 자율 실행 정책을 점진 도입한다. 유료 사용 허용 목표와 이번 지출 권한을 구분한다.
- 완료 조건: 예산 상한·중단·보고·복구·담당자가 정해지고 비용 미확정 시 신규 유료 호출이 발생하지 않는다.
- 소유자 / 기한: 운영 + Owner / G2.

## 5. 권장 아키텍처

아래는 상세 설계의 기본 제안이다. 제공자·호스팅 계약을 확인하기 전 특정 제품 선택을 확정하지 않는다.

```text
Owner / 개발 검토
  → 버전이 있는 정책·예산·승인 기록
  → n8n: 스케줄·작업 전달·재시도
      → 조사/초안: 제한된 모델·근거 묶음
      → 검증: 규칙 검사 + 사실 검토
      → 승인된 콘텐츠 revision
      → Git 검토·빌드 → 운영 호스팅 배포 → URL/버전 확인

방문자 → 공개 사이트 → 공급자 발행 제휴 링크 → 공급자 구매·예약
                    └→ 비동기 클릭 이벤트 → 제한된 수집 API/수집 저장소

공급자 CSV/API → 보존 원본 → 정규화·격리 → 전환/수수료/지급 기록
수집 이벤트 + 공급자 보고 → PostgreSQL 원장·집계 → 규칙 기반 판단
                                                └→ AI 설명 → Owner 보고
```

- 운영 제어면(n8n 편집기, DB, 비밀, 배포 권한)은 비공개다. 외부 클릭 수집은 좁은 계약만 노출한다.
- 공개 페이지와 구매 이동은 iMac·모델·수집기의 정상 동작에 의존하지 않는다. 수집 실패는 측정 누락으로 기록한다.
- n8n은 흐름을 조정한다. 돈 계산·중복 방지·귀속 규칙은 버전 관리된 결정론적 코드/SQL이 담당한다.
- Git은 코드·템플릿·정책의 기준점, DB는 작업 상태·승인·정산의 기준점이다. 원본 보고서는 접근 제한 저장소에 두고 Git에는 샘플과 해시·스키마만 둔다.
- 배포 결과와 승인 버전은 DB가 참조한다. Git의 변경 파일과 DB 본문이 동시에 독립 원본이 되지 않게 콘텐츠 원본 소유권을 ADR로 확정한다.
- 초기에는 기존 PostgreSQL과 작업 큐 기능을 우선 검토한다. 새 브로커·다수 마이크로서비스 도입은 실제 한계가 입증된 뒤 결정한다.

## 6. 공급자 계약을 먼저 확정하기

공급자 목록에 이름이 있다는 것과 사용 가능한 수익 경로가 있다는 것은 다르다. 첫 공급자마다 다음을 작성한다.

| 항목 | 기록할 내용 | 통과 기준 |
|---|---|---|
| 자격 | 계정 승인, 게시 도메인, 판매자 국가, 지급 국가 | 실제 이용 가능 근거 |
| 고객 적합성 | 구매자 국가, 언어, 결제·배송·예약 지원 | 첫 고객군이 구매 가능한 경로 |
| 링크 | 공식 생성 방식, 허용 파라미터·추적 ID, redirect 허용 여부 | 정책 근거와 생성 샘플 |
| 보고 | CSV/API/수동, report type, 행 단위, 기간, 시간대 | 익명화 샘플과 컬럼 매핑 |
| 귀속 | 클릭별/추적 ID별/상품별/프로그램별 가능 범위 | 지원·미지원·미확인 명시 |
| 정산 | 주문·확정·취소·수정·지급의 의미와 지연 | 원장 상태 매핑과 지급 대사 방식 |
| 콘텐츠 | 고지, 이미지·가격 사용, 갱신·보존 조건 | 정책 URL·확인일·검토자·유효 버전 |
| 운영 | 보고 갱신 주기, 실패 대체 경로 | 수동 수입을 포함한 복구 절차 |

지원하지 않는 기능은 `unsupported`, 아직 확인하지 못한 기능은 `unknown`으로 구분한다. 광고 추적 파라미터를 임의로 만들거나 공급자가 되돌려준다고 가정하지 않는다.

Amazon 공식 Order Report 안내는 상품 단위 항목, 다른 상품 주문, 클릭과 주문의 기간 불일치를 설명한다. 따라서 상품 ID·같은 날짜의 클릭만으로 일대일 귀속을 보장할 수 없다는 설계 판단이 따른다. 이는 모든 공급자의 세부 기능을 검증했다는 뜻은 아니다. [Amazon Order Report](https://affiliate-program.amazon.com/help/node/topic/GPTZ495QPL6TEZLJ).

## 7. 데이터 모델 보완 명세

다음은 논리 모델이다. 각 항목을 반드시 별도 물리 테이블로 만들라는 뜻은 아니다. G1에서 실제 보고서와 기존 DB를 대조해 통합 가능한 항목을 결정한다.

### 7.1 식별자·관계·측정 단위

| 논리 객체 | 최소 계약 |
|---|---|
| Program account / policy | 공급자와 실제 계정 구분, 시장, 통화, 정책 버전, capability, 확인일, 비밀 자체 대신 credential reference |
| Experiment | 고객군·시장·언어·프로그램·유입 채널, 콘텐츠 집합, 주지표, 기간·예산·결정 규칙 버전 |
| Content / revision | 영구 content ID와 불변 revision ID, 본문 해시, 언어·대상 시장, 검토 상태, 근거와 공개 URL |
| Affiliate item / offer | 대상 상품·서비스, 공급자 ID, 원본 URL, 자료 시점, 가격·통화, 사용권·유효 상태 |
| Link / placement version | `link_id`, content revision, 배치, offer, 공급자 추적 ID, 공식 affiliate URL, 유효 시작·종료 시점 |
| Click event | `event_id`, `link_id`, event time·received time, 수집 버전, 측정 동의 상태(해당 시), 분류·제외 사유 |
| Import batch / raw row | program account, report type·기간·timezone·revision, 파일 해시, 원본 참조, 행 식별자, 수입 결과 |
| Conversion / report fact | 공급자 행의 실제 단위, 주문/항목/집계 구분, 원시 상태, 정규화 상태, 수량, 통화·금액, 원본행 FK |
| Attribution mapping | 공급자 키 → link/content/experiment 연결, 유효 기간, 귀속 수준, 매핑 근거·버전, 미귀속 사유 |
| Commission adjustment | 중복 방지 키, 전환/원본행 참조, 금액 증감, 상태/사유, 기준 날짜, 원장 반영 버전 |
| Payout / receipt | 공급자 지급 배치와 실제 입금 증거, 지급·입금일, 금액·통화, 수수료·원천공제, 미대사 차이 |
| Cost / time entry | 지출 또는 미지급 구분, 직접/공통, experiment/content 귀속, 지급일, 통화, 배부 정책, Owner 시간 |
| Publication / approval | 승인 대상 revision·정책, 권한자, 만료, action key, deployment ID, Git commit, URL, 검증 결과 |

전환 보고서가 일별 상품 집계라면 그 행을 가상의 주문으로 분할하지 않는다. 개별 `external_conversion_id`가 없는 공급자는 `report_fact` 구조로 수입하고 전환 건수의 정의를 명시한다.

### 7.2 귀속 수준

- `content_exact`: 공급자가 반환한 키가 해당 콘텐츠에 고유하게 대응하는 경우. 개별 방문자를 알 수 있다는 의미는 아님.
- `experiment_exact`: 실험 단위 추적키까지만 구별되는 경우.
- `program_only`: 프로그램 총액·상품까지만 알려져 실험별 배분이 불가능한 경우.
- `unattributed`: 연결 키가 없거나 매핑 충돌이 있는 경우.
- `estimated_allocation`: 별도 관리 추정. 공식 귀속 금액과 분리하고 모델·분모·가정·버전을 표시한다.

하나의 추적 ID를 여러 실험이 공유하면 정확한 실험 수익을 표시할 수 없다. 그 경우 공급자가 허용하는 더 세밀한 ID를 쓰거나 실험 기간·범위를 분리하고 오염 가능성을 기록한다.

귀속 불명 금액도 전체 공급자 매출에는 포함한다. 다만 어느 글이 벌었는지 확정하지 않는다. 하나의 금액이 두 카테고리에 전액 귀속되지 않도록 주 카테고리 또는 배부 규칙을 둔다.

### 7.3 불변조건과 수입 규칙

1. FK·고유키·필수값·상태 제한을 실제 DDL에 명시한다. 통화는 코드, 시간은 timezone을 보존하는 형식, 금액은 소수 오차 없는 decimal/minor-unit 계약을 사용한다.
2. 파일 해시는 같은 파일의 중복을 막을 뿐이다. 기간이 겹치는 서로 다른 파일에는 별도의 공급자 행 키·수정 시각·스냅샷 범위 규칙이 필요하다.
3. 행 키는 보고서 의미에 맞게 결정한다. 예: 계정 + 보고서 유형 + 주문 ID + 주문항목 ID. 실제 필드가 없으면 임의 주문키를 만들지 않고 집계의 차원·기간·revision으로 대체한다.
4. 동일 키 재수입은 중복 insert가 아니라 무변경 또는 버전 갱신이다. 금액 수정은 이전 상태와 차이를 보존한다.
5. 원본 저장 → 구문 검사 → 정규화·격리 → 대사 → 원장 반영을 구분한다. 원장 쓰기와 수입 상태 완료는 동일 트랜잭션 또는 복구 가능한 상태 계약으로 처리한다.
6. 필수 컬럼 삭제·통화 오류·알 수 없는 상태는 격리한다. 전체 성공으로 보고하지 않는다. 격리 행이 있으면 데이터 품질은 `partial`이다.
7. 취소·정정은 원장 이력으로 남기며, 기존 양수 금액 테이블 제약을 임의로 제거하지 않는다. 잔액 계산과 상태 호환 방식을 설계한다.
8. Click의 `event_id`는 중복 방지용이다. 동일 ID가 다시 오면 중복 저장하지 않는다. 공개 이벤트는 위조 가능하므로 provider 보고와 같은 신뢰도로 취급하지 않는다.
9. 수집 안 됨·보고 지연·추적 불가를 0으로 저장하지 않는다. `available / delayed / partial / unavailable / not_applicable`과 `data_as_of`를 둔다.

### 7.4 기존 시스템 연결

- 기존 `content`, `approvals`, `experiments`, `executions`, `agent_actions`의 상태·키·소비자를 조사해 확장한다. 신규 `affiliate` schema 사용 여부는 충돌 방지와 운영 복잡성을 비교해 결정한다.
- 기존 `revenue`와 새 수수료 원장은 동시에 독립 집계하지 않는다. 새 원장을 채택한다면 기존 보고용 `revenue`는 provenance가 있는 파생 투영으로 만들거나 뷰로 연결한다.
- `revenue_channel_metrics`는 일별 조회용 집계로 취급한다. 신규 정확성·신선도 상태를 별도 필드/뷰로 드러내고 기본값 0이 미수집으로 해석되지 않게 한다.
- 실제 DB와 체크인 migration이 동일한지는 아직 미검증이다. 운영 schema snapshot과 소비자 목록을 G0에서 비교한다.

## 8. 수익·비용·KPI 계약

### 8.1 구분할 값

- 예상 수수료: 미확정 주문·예약에서 기대하는 금액. 현금으로 표시하지 않는다.
- 공급자 확정 순수수료: 공급자에서 확정한 수수료에서 취소·환불·정정을 반영한 금액. 지급 전 잔액을 포함할 수 있다.
- 실제 입금: 입금 증거와 연결된 현금 유입. 공급자 지급 통보와 실제 입금 확인을 구분한다.
- 콘텐츠 공헌이익: 같은 귀속 기준의 확정 순수수료 − 직접 제작·배포·유지 비용. 제작비 일시 반영 또는 기간 배분을 표시한다.
- 사업 순현금흐름: 해당 기간 실제 입금 − 실제 사업 현금지출. 투자·Owner 자금 투입은 영업 성과와 구분한다.
- Owner 시간: 실제 분·시간과 작업 종류를 기록한다. 시간의 추정 비용은 별도 경제성 지표이며 지출 없는 값을 현금지출에 더하지 않는다.
- 공통비: 호스팅·도구 등 직접 귀속 불가 비용은 명시된 규칙으로 배부하거나 공통비로 남긴다. 두 번 차감하지 않는다.

이 정의는 내부 관리 지표 제안이다. 회계·세무상 매출 인식이나 신고 기준의 확정은 별도 검토 대상이다.

### 8.2 지표 정의

| 지표 | 정의 | 제한 |
|---|---|---|
| Affiliate session CTR | 유효 제휴 클릭을 1회 이상 한 측정 세션 / 해당 상업 페이지의 측정 세션 | 동일 측정 체계·기간 사용. 동의/차단으로 전체 방문자를 대표하지 않을 수 있음 |
| Click events per session | 유효 클릭 이벤트 / 측정 세션 | 반복 클릭으로 1보다 클 수 있음. 위 CTR과 구분 |
| Provider EPC | 공급자 동일 보고 범위의 순수수료 / 공급자가 보고한 클릭 | 확정/예상 표시, 보고 기준·기간·통화 일치 |
| Observed-click EPC | 동일 귀속 범위 순수수료 / 자체 유효 클릭 | 손실·봇 분류의 영향을 받으며 Provider EPC와 별도 명칭 |
| Provider conversion rate | 공급자가 정의한 전환 단위 / 호환되는 공급자 클릭 단위 | 주문·상품 수량·예약 완료를 혼합하지 않음 |
| Revenue per 1,000 sessions | 동일 범위 확정 순수수료 / 측정 세션 × 1,000 | 공급자 지연으로 기간 불일치 가능, 최신 기간은 provisional 표시 |
| Attribution coverage | 콘텐츠/실험에 근거로 배분 가능한 수수료 / 해당 공급자 수수료 | content와 experiment coverage를 분리 |
| Owner load | 직접 운영 시간 / 기간 | 대기 승인 건수·최장 대기시간도 병기 |

0분모는 `N/A`, 미수집은 `unavailable`이다. 총수익 0 또는 순정정이 음수인 기간의 coverage 비율은 `N/A`로 두고 귀속 금액과 미귀속 금액을 표시한다. 국가 비교는 공통 통화 환산 정책을 사용하며 원통화 금액·환율 출처·적용일을 남긴다.

원문의 `Traffic × CTR × CVR × AOV × Commission rate`는 가설 계산에 사용할 수 있다. 실제 원장에는 공급자 보고 금액을 사용하고, CPA/정액 수수료·주문한도·상품별 예외·취소를 adapter에서 처리한다. 다른 기간의 클릭과 주문으로 만든 비율은 코호트 전환 확률처럼 설명하지 않는다.

### 8.3 정산 인수 테스트 — 가상 KRW 사례

| 사건 | 기대 결과 |
|---|---|
| 예상 수수료 10,000 | 예상 10,000, 확정 0, 입금 0 |
| 전액 확정 | 예상 잔액 0, 확정 누계 10,000, 입금 0 |
| 확정 후 2,000 취소 | 확정 순수수료 8,000, 조정 이력 -2,000 |
| 지급 시 수수료 500 공제, 실입금 7,500 | 공급자 잔액에서 8,000 지급 정산, 입금 7,500, 공제 500을 별도 대사 |
| 다른 사업 현금지출 3,000 | 순현금흐름 4,500. 입금에서 이미 공제된 500을 다시 차감하지 않음 |
| 동일 파일·겹치는 기간 보고서 재수입 | 기존 금액 불변 |

전환을 만든 고객의 자연 구매와 정산은 외부 사건이다. 테스트를 위해 실제 제휴 링크 자동 클릭·자가 구매로 전환을 만들지 않는다.

## 9. 작업 상태와 승인 계약

### 콘텐츠

`draft → researched → qa_passed → approval_pending → approved → deploying → published`

실패 경로는 `qa_failed`, `rejected`, `expired`, `deploy_failed`로 구분한다. 이것은 새 논리 상태 제안이며 기존 DB status 값을 바로 치환하는 명세가 아니다.

- `qa_passed`는 정책·필수 검사·사실 검토 증거가 충족되었다는 뜻이다.
- 승인에는 revision·정책 버전·허용 행동·권한자·시각·만료를 묶는다. 승인 후 본문 또는 링크 변경은 승인 재평가 대상이다.
- 게시 재실행 키는 콘텐츠 revision + target + action으로 만든다. 배포가 성공했는데 DB 기록이 실패하면 deployment ID와 공개 본문 버전으로 복구한다.
- URL HTTP 200뿐 아니라 기대 제목·본문 해시/버전·제휴 고지·링크·canonical을 확인해야 `published`다.
- KEEP는 기존 상태 유지, UPDATE는 새 revision, EXPAND는 별도 범위의 실험 제안이다. KILL은 신규 투자·생산 중단을 뜻하며 기존 URL 삭제를 자동 의미하지 않는다.
- 최초 파일럿은 기존 게시 승인 경로를 유지한다. 이후 사전 승인된 시장·프로그램·위험·예산 범위의 자동 게시 정책을 별도 설계할 수 있다.

### 수입·정산

`received → validated → normalized → reconciled → posted`와 `quarantined / failed`를 둔다. 정산서 원본과 상태 수정 이력은 보존한다.

### 작업 실행

- `job_key`, 실행 원인, lease 만료, attempt, 다음 재시도 시각, 결과 참조를 기록한다.
- 네트워크 오류는 공급자 정책에 맞춰 제한 재시도한다. 인증·스키마·권한·정책 오류는 즉시 반복하지 않고 조치 필요 상태로 전환한다.
- 알림 중복키는 작업/사건 ID + 상태 전환이다. 같은 사건의 재시도마다 Owner에게 새 승인을 요청하지 않는다.
- 각 단계 timeout·retry 수치는 adapter별 확정한다. 모든 단계에 동일 횟수와 무제한 retry를 쓰지 않는다.

## 10. 콘텐츠·AI·클릭 측정 보완

### 콘텐츠의 실질적 가치

첫 3–5개 글은 비교 기준, 자료 시점, 누구에게 맞고 맞지 않는지, 가격 외 비용·조건, 선택 이유를 제공해야 한다. 현장 경험·직접 테스트는 실제 증거가 있을 때만 주장한다. 형식 검사 통과와 독자에게 새로운 가치가 있다는 판단은 분리한다.

각 중요한 주장에는 근거 URL, 관찰일, 적용 국가, 만료·재검토 조건을 붙인다. 상품 이미지·표·여행 사진은 사용권과 출처를 기록한다. 가격·할인·운항·공연·비자·건강 관련 정보는 위험과 변동성에 맞게 재검토한다. 이번 리뷰는 개별 법률·의학 정보의 정확성까지 승인하지 않는다.

경제적 관계 고지는 사람이 읽을 수 있게 표시하고 공급자·시장에 맞는 문구를 검증한다. 제휴 링크의 검색엔진 관계 표시는 `rel="sponsored"`를 기본 제안으로 한다. 이는 화면의 고지를 대체하지 않는다. Google은 광고·유료 링크에 sponsored를 권장하고 nofollow도 허용한다. [공식 링크 속성 안내](https://developers.google.com/search/docs/crawling-indexing/qualify-outbound-links).

### AI 역할과 평가

- AI: 근거 요약·초안·분류·판정 설명. 모델의 confidence는 검증된 정확도 확률로 취급하지 않는다.
- 코드/SQL: 금액·점수 산식·예산 한도·상태 전환·승인·중복 방지·최종 집계.
- 외부 문서·검색 결과·보고서 텍스트는 비신뢰 입력이다. 입력의 지시문이 도구 권한·승인 정책을 바꾸지 못하게 한다.
- 모델 기록: 제공자·모델/버전·프롬프트 버전·근거 묶음 해시·출력·시간·비용·검토 결과.
- 초기 회귀 세트 제안: 정상 10개, 사실/가격 오류 5개, 허위 후기·고지 오류 5개, 주입·권한 이탈 5개, 공급자 실패·근거 만료 5개. 총 30개는 초기 개발 기준이며 통계적 안전 보장은 아니다.
- 출시 기준 제안: 해당 세트에서 고위험 행동·고지 누락·허위 경험을 모두 차단하고, 첫 파일럿 초안 100%를 사람 또는 명시된 독립 검토 단계가 확인한다. 동일 모델의 자기 검수만으로 승인하지 않는다.
- 로컬 모델 우선은 현재 운영 제약으로 유지한다. 문서가 유료 도구 사용을 허용하는 방향이어도 예산·사용 정책이 정해지기 전 신규 유료 호출 권한이 생기는 것은 아니다.

### 측정과 개인정보

- 링크는 공급자 발행 URL을 유지하고, 수집은 비동기 방식으로 한다. redirect 방식은 공급자 허용과 안전성이 확인될 때만 선택한다.
- 공개 링크 건강 검사는 허용된 API·비추적 대상 URL·정적 형식 검사 등을 우선 사용한다. 제휴 추적 링크를 자동으로 반복 방문하면 인위적 클릭을 만들 수 있다. 403·검사 실패를 곧바로 상품 판매 종료로 확정하지 않는다.
- 이벤트에는 배포 시 생성한 유효 link ID·revision만 허용한다. 브라우저가 제출한 금액·전환은 원장에 반영하지 않는다.
- 브라우저에 공유 비밀을 넣지 않는다. CORS·Origin 확인은 보조 통제이며 인증이나 봇 방지의 대체 수단이 아니다.
- 수집 payload 크기·허용 필드·rate limit·중복·보존을 정의한다. referrer는 불필요한 query/fragment를 제거하고 개인정보 가능성을 줄인다.
- raw IP·전체 사용자 에이전트·장기 session ID는 필요성이 입증되기 전 수집하지 않는 것을 기본 제안으로 한다. gateway 로그와 분석 도구 설정도 함께 확인한다.
- 익명 원시 이벤트 30일·집계 13개월은 초기 보존 제안값이다. 적용 시장의 정책·동의·삭제 요구 확인 후 확정하며 법적 기준으로 해석하지 않는다.
- 테스트 이벤트는 staging 또는 별도 표식·저장소에 두고 실제 KPI에서 제외한다. 로그 차단·동의 거부·이벤트 손실을 정상 전환 0으로 간주하지 않는다.

## 11. 사업 실험과 의사결정 개선

### 첫 실험 범위

고객군 1개, 대상 시장 1개, 언어 1개, 공급자 1개, 콘텐츠 3–5개, 핵심 구매 여정 1개를 권장한다. 예시인 Korea Travel + K-pop은 후보 가설로 남긴다. 기존 IT 카테고리 역시 자동 탈락·선정하지 않는다.

선정 순서는 실제 제휴 이용 가능성 → 고객 구매 가능성 → 유입 근거 → 차별적 콘텐츠 제작 가능성 → 예상 공헌이익이다. 단일 공급자로 시작하는 것은 검증 복잡도를 줄이기 위한 제안이며, 확장 단계에는 집중 위험과 대체 경로를 평가한다.

첫 유입 검증에는 검색 의도 묶음, 경쟁 페이지에서 해결되지 않는 질문, 허용된 배포 채널, 실제 고객 피드백 수집 방법을 포함한다. 원문의 카테고리 추천만으로 검색 수요와 수익성을 확정하지 않는다. 유료 광고는 별도 예산이 있는 실험에서만 검토한다.

### 점수

- 자격 탈락: 제휴 사용 불가, 고객 구매 불가, 정책 불가 등은 높은 총점으로 상쇄하지 않는다.
- 증거 부족: 수요·수수료·경쟁도 출처가 없으면 `needs_evidence`로 보류한다.
- 점수 계산: 각 항목 0–5 기준 설명과 `weight × value / 5`를 버전으로 고정한다. 경쟁도는 높은 점수가 쉬운 시장을 뜻하도록 방향을 통일한다.
- AOV와 예상 수수료는 같은 경제 효과를 이중 가중할 수 있다. 가중치는 초기 가설로 표시하고 실제 성과로 재검증한다.
- 점수는 실험 우선순위다. 자동 지출·카테고리 확대 권한으로 사용하지 않는다.

### 결정 규칙

| 조건 | 결과 |
|---|---|
| 추적 미설치·수입 실패·미성숙 보고·소표본 | `WAIT_FOR_DATA`, 원인과 다음 확인일 표시 |
| 정책 또는 계정 사용 불가 | 해당 프로그램/오퍼 PAUSE, 필요하면 수동 검토 |
| 유입은 있으나 클릭 낮고 콘텐츠·오퍼 불일치 증거 있음 | UPDATE 실험 제안 |
| 성숙 데이터에서 반복 전환·양의 공헌이익·감당 가능한 유지비 | 제한된 EXPAND 제안, 예산과 잔여 불확실성 포함 |
| 사전 중단 기준 충족, 측정 정상, 개선 가설 소진 | 신규 투자 중단 제안. URL 처리는 별도 결정 |

7일은 기술·색인·링크 점검, 30일은 초기 학습, 90일은 포트폴리오 검토다. 보고가 늦거나 계절성이 크면 달력만으로 결론을 강제하지 않는다. 원문 §37의 6개월 안정성 지표는 90일 실험에서는 `not_yet_observable`이다.

표본 기준은 목표 수익성과 예상 전환율에 따라 G0에서 계산한다. 예를 들어 독립적인 성숙 클릭, 일정 전환 확률 1%, 완전한 관측을 가정하면 0건 확률은 `(1−0.01)^n`이다. 약 299클릭에서 5% 아래가 된다. 이 값은 설명용 계산이며 보편적 중단 기준이 아니다. 반복 사용자·지연·귀속 손실이 있으면 이 가정이 깨진다.

## 12. 운영 목표와 인수 테스트

아래 수치는 새 서비스의 초기 제안값이며 실측 성능이나 승인된 SLO가 아니다. 비용·호스팅·공급자 주기에 맞춰 G0에서 확정한다.

| 방문자 경로 | 수집 API·iMac·모델 중단 중에도 페이지와 제휴 이동 가능 |

## 13. 다시 정렬한 구축 로드맵

각 단계의 작업량은 일정을 보장하는 추정이 아니다. 외부 승인·자료가 없으면 해당 의존 작업을 보류하고 독립적인 로컬 설계·테스트를 계속한다.

| 순서 | 작업 패키지 | 산출물 | 선행 조건 | 완료 조건 / 담당 |
|---|---|---|---|---|
| B01 | 현행 구조·소유권 확인 | 기존 테이블·워크플로·배포 경로 재사용 매핑, 변경 기준 브랜치 | 원본과 이 리뷰 | 충돌·중복 실행 위험 목록 완료 / 아키텍처 |
| B02 | 첫 실험·호스팅·권한·비용 결정 | experiment brief, ADR 묶음, 예산·Owner 역할 | B01 | G0 항목 결정 / Owner + 설계 |
| B03 | 공급자 1곳 계약 조사 | capability, 익명화 보고 샘플, 데이터 사전 | 후보 조사, 실제 계정 정보는 필요한 범위만 | 사용·보고·정산 의미 검증 / 제휴 운영 |
| B04 | 귀속·정산 상세 명세 | ERD, 키·상태·집계 계약, 테스트 fixture | B01/B03 | T01–T05의 기대값 계산 가능 / 데이터 |
| B05 | 격리 수입·정산 구현 | migration 초안, import·reconcile 모듈, 단위/통합 테스트 | B04, 후속 구축 요청 | G1 통과, 실제 운영 DB 무변경 / 구현 |
| B06 | 클릭·콘텐츠 revision·승인·게시 설계/구현 | 이벤트 계약, publisher 연결, QA와 승인 테스트 | B02/B05 | T06–T10·T12 통과 / Backend·보안·운영 |
| B07 | 소규모 공개 파일럿 | 콘텐츠 3–5개, 배포 증거, 측정 상태 | G2 및 필요한 게시 권한 | 정상 사용자 경로·실제 보고 회수 확인 / 콘텐츠·운영 |
| B08 | 실험 평가 | 성숙 보고, 비용·귀속 수준, 판단 근거 | B07, 자연 유입·보고 대기 | G3 판정, 증거 부족은 보류 / 사업·분석 |

핵심 순서 변경은 **공급자·보고서 확인 → 귀속·정산 검증 → 클릭·승인·게시 검증 → 첫 콘텐츠 공개 → 실험 평가 → 확대**다. Category Scout, 다국어 양산, Gmail·Calendar 확장은 첫 루프의 핵심 의존성이 아니라 후속 선택 항목이다.

## 14. 게이트와 결정 대기 목록

### G0 — 상세 설계 기준 확정

- [ ] D01: 첫 고객군·시장·언어와 3–5개 콘텐츠 범위. 제안: 한 개씩 시작. 결정권자 Owner, 조사 담당 사업.
- [ ] D02: 첫 제휴사·보고서 취득 경로. 실제 자격·보고서 검증 후 결정. 담당 제휴 운영.
- [ ] D03: 상업 이용에 맞는 호스팅과 도메인·이전 정책. 담당 아키텍처, 지출 결정 Owner.
- [ ] D04: 예산·Owner 시간 목표·운영 책임. 숫자는 미정. 결정권자 Owner.
- [ ] D05: 기존 테이블/워크플로 재사용과 정산 원장·콘텐츠 원본 소유권. 담당 아키텍처·DBA.
- [ ] D06: 초기 승인 정책과 추후 자율 게시 허용 범위. 제안: 최초 개별 승인, 확대 시 범위 승인 검토. 결정권자 Owner.
- [ ] D07: 대상 시장의 측정·보존·동의·공급자 콘텐츠 정책. 담당 운영·보안, 전문 판단이 필요한 부분 별도 표시.

이 항목들은 현재 사용자에게 반복 확인을 요구하는 목록이 아니다. 후속 작업은 파일·계정·공식 자료로 확인 가능한 사실을 먼저 채우고, Owner의 선호·지출·권한 결정만 묶어서 요청한다.

### G1 — 수입·귀속·정산 준비

- [ ] 실제 형식 샘플로 수입·취소·정정·중복 테스트 통과.
- [ ] 보고 단위와 귀속 한계 명시, 미귀속·미수집 보존.
- [ ] 금액·환율·공제·비용·현금 계산 계약 확정.
- [ ] 기존 DB와의 migration·호환성·복원 계획 검토 완료.

### G2 — 공개 파일럿 준비

- [ ] 운영 호스팅·프로그램·도메인 사용 조건 확인.
- [ ] 승인 revision, QA, 고지, 출처·이미지 권리 확인.
- [ ] 비동기 클릭 측정과 수집 장애·악용 테스트 통과.
- [ ] 배포·DB 불일치 복구, 이전 버전 복구, 경보 수신 검증.
- [ ] 미해결 P1 없음. 공급자 정책이나 사용 제한은 내부 위험 수용만으로 면제하지 않음.

### G3 — 확대 판단

- [ ] 유효한 실제 유입·성숙 보고·자연 전환 증거.
- [ ] 귀속 가능한 범위에서 반복 전환과 공헌이익 평가.
- [ ] 유지비·Owner 시간·집중도·취소율 검토.
- [ ] 다음 실험의 예산·가설·수량·중단 기준 지정.

## 15. 완료를 세 단계로 구분

1. **구축 완료:** 테스트 데이터로 전체 흐름·오류·복구·정산 정확성을 검증하고 운영 인수 기준 충족.
2. **실거래 연동 검증 완료:** 허용된 실제 보고서 수입, 발생한 자연 전환의 수수료·지급·입금을 증거로 대사. 아직 입금이 없으면 해당 단계 미검증으로 표시.
3. **사업 검증 완료:** 반복 유입·전환·양의 공헌이익·현금흐름·감당 가능한 Owner 시간이 사전 기준 충족.

원문의 §43은 구축 완료와 사업 검증을 섞고 있다. 전환이 없어도 수입·대사 소프트웨어의 정확성을 테스트할 수 있고, 반대로 전환 1건이 있어도 사업성이 검증된 것은 아니다.
